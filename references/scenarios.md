## 使用前约定

这些流程由 AI 执行，不是让新手照抄命令。先读 `safety-rules.md` 与 `ai-review-flow.md`。

- 根据用户已给的信息、实际目录和远端判断情景；仍不清楚时用日常语言询问。
- 先解析实际安装目录为 `SKILL_DIR`，从目标项目目录调用 `bash "$SKILL_DIR/scripts/preflight.sh"`。不要运行项目中碰巧同名的脚本。
- 下文 `$BASE_REMOTE`、`$BASE_BRANCH`、`$TASK_BRANCH`、`$BASE_SHA`、`$STASH_SHA` 等均是 AI 从真实环境核验后设置的变量。未设置或有歧义时停止，不能照抄空变量或猜 main。
- 本地状态、联网查询、文本冲突、业务逻辑、测试和正式审批是不同检查。任何一项未完成就如实记录。
- 保留项目已有约定，不擅自重命名默认分支、覆盖配置、改仓库公开性或部署生产。
- `.gitignore` 不能保护已经跟踪的秘密。先审查未暂存和已暂存 diff，再按明确路径暂存；不默认 `git add -A`。
- 凭证决定 GitHub 操作账号，`user.name/user.email` 只决定提交署名。使用用户确认的身份，不借别人的登录态。
- fetch 会刷新本地 Git 元数据，但不会自动把远端文件合入工作区。检查最新信息不等于自动修改代码。

## 情景 1：单人从零起步

**适用回答**：“现在没有代码，先我自己开始。” 若朋友已参与，初始化后接情景 2 或 5。

### 初始化

1. 确认目标项目位置、Git 是否安装、是否已有文件或父级 Git 仓库。不是空目录则转附录 A；不要在已有项目上重复初始化。
2. 确认 GitHub 账号、新仓库名称、公开或私有。**上传公开不是备份的默认选择**。
3. 在用户授权的新目录初始化 Git，建立适合技术栈的 `.gitignore`，说明 README 等首批文件来源。
4. 核验本仓库的提交署名；需要配置时只设本仓库，不擅改全局。
5. 审查首批文件及暂存区，再首次提交。通过可用网页、CLI 或 API 新建空远端，确认 remote URL 后推送指定分支。
6. 回读远端提交和可见性，不能只凭 push 命令返回就宣称完整发布。

### 日常

- 用户可选择简化的单人主线开发，或使用临时功能分支。已有保护规则时仍走 PR。
- 每次只提交属于当前任务的内容；小步测试与提交。
- 单人多电脑或多个 AI 同时工作也可能分叉。出现非快进拒绝时按安全同步规则处理，不强推。
- 朋友加入后切换双人流程，不能继续用单人自检冒充互审。

## 情景 2：双机协作者（推荐）

**适用回答**：“各用各的电脑，朋友已经被加为协作者。”

### 建立协作

1. 仓库维护者邀请用户明确指定的 GitHub 账号；对方接受后核验实际权限。不能靠绿色 Code 按钮判断写权限。
2. 双方各自 clone，独立登录、独立工作目录，不共享令牌或 SSH 私钥。
3. 按 `gates-setup.md` 配置并核验主线保护、互审和实际可运行的 CI。新 CI 先跑通，再成为必需检查。
4. 确认谁负责哪些功能。双方 AI 可在授权范围内创建 Draft PR 描述任务；未上传代码对对方不可见。

### 开工、提交和合并

1. 预检本地，联网查看真实目标主线、双方分支和所有可见 PR。对相关改动读 diff，而不是只数提交。
2. 核实目标主线 SHA 后，从该 SHA 创建独立任务分支；不要从未知旧功能分支随意分叉。
3. 开发、测试、按明确路径提交并推送自己的任务分支。推送前重查远端；没完成的工作可保持 Draft，不合进主线。
4. 准备合并时，将目标主线更新合入自己的功能分支，保留已发表历史。先做隔离文本预演，再实际合并并测试；不能根据“没报冲突”直接认为业务正确。
5. 朋友的 AI 辅助审你的 PR，你的 AI 辅助审朋友的 PR。作者可自检评论，但不能正式批准自己的 PR。
6. 记录审核的 base/head SHA、问题、测试和缺口；新提交或主线变化后重新核验。
7. 在真实审批、必需检查和用户授权都满足时合并。可选 Squash Merge，遵守项目实际规则。
8. 核实远端结果；只有任务结束且无人继续依赖时才清理该任务分支。部署是独立动作，不由本流程擅自触发。

### 常见阻塞

- 无权限：停在本地，不尝试换别人的凭证；可切情景 5。
- PR、测试或保护状态 UNKNOWN：补足查询，不能当绿灯。
- 两边需求矛盾：AI 用业务语言列出差别和推荐，让用户决定。

## 情景 3：同机轮流

**适用回答**：“同一台电脑，一人用完另一人再用。”

- 推荐每人使用独立系统账号或独立 clone，保留各自的凭证与署名。
- 如果轮流使用同一工作目录，必须确保前一人已经结束操作。先记录分支、未提交改动归属，再交接。
- 有未提交工作时，不能让后一人直接提交它。由所有者决定完成提交或按准确 SHA 暂存保存。
- stash 默认不含新文件；选择 `-u` 前核查新文件。恢复按稳定 SHA 查看和 apply，不用默认 pop 最新一条。
- 改 `git user.name/email` 不会切换 GitHub 登录账号。正式 review/push 仍核验实际凭证。
- 日常采用情景 2 的独立任务分支和 PR。需要同时工作时，切换情景 4，不依赖“大家小心一点”。

## 情景 4：同机多个 AI 并行

**适用回答**：“我想同时开两个 AI，各做各的。”

1. 查看现有 worktree 和正在使用的目录，不切换或修改别人的活跃工作区。
2. 核验远端最新基线，给新任务创建独立 worktree 和独立分支；明确新目录位置，不在用户未授权目录随意写入。
3. 可以从已经核验的 SHA 创建，不必先切换主工作区：

```bash
# 以下变量必须事先核验；目标目录不存在且已获授权。
: "${TASK_DIR:?}" "${TASK_BRANCH:?}" "${BASE_SHA:?}"
git worktree add -b "$TASK_BRANCH" "$TASK_DIR" "$BASE_SHA"
```

4. 每个 AI 只在自己目录内读写、测试、提交，合并仍走 PR。
5. worktree 共享 Git 对象和部分配置；`git config --local` 的身份可能影响其他 worktree。不同人的身份推荐独立 clone/系统账号；独立 clone 也不自动隔离全局凭证。
6. 端口、外部数据库、共享缓存和构建输出不会自动隔离。AI 应检查并配置各自测试资源，不碰生产数据库。
7. 只删除已确认结束的 worktree，不用强制删除清除别人未提交的工作。

## 情景 5：Fork 贡献

**适用回答**：“朋友能读，但不能直接把代码推回原仓库。”

- 原仓库是 PR 的目标；自己的 fork 是推送目标。常见命名是 `upstream` 与 `origin`，但必须实际核验，不能按名字猜。
- 获取 fork 并 clone，添加经过用户确认的原仓库 remote，不覆盖已有 remote。
- fork 的基础分支只跟随原仓库；自己的功能放独立任务分支。基础分支分叉时停止调查，不强制重置。
- 每次开发前刷新原仓库基线；显式将原仓库分支传给远端检查，不能把 fork 的默认分支误当原仓库最新状态。

```bash
: "${SKILL_DIR:?}" "${BASE_REMOTE:?}" "${BASE_BRANCH:?}"
bash "$SKILL_DIR/scripts/remote_check.sh" --base "$BASE_REMOTE/$BASE_BRANCH"
```

- 推送至自己的 fork 后，核对 PR 的 base repository/base branch 与 head repository/head SHA。
- fork PR 的 head 对象可能不在普通 fetch 的分支列表里；AI 需通过已核验的 PR ref 获取对象，再校验 SHA。
- 不能为运行外部 PR 自动授予生产密钥或提升 Actions 权限。
- 审查、隔离试合、测试与合并沿用情景 2。

## 情景 6：直接共享主线（仅明确选择时）

**适用回答**：“小实验，我明确不想用 PR。”

先解释：普通 push 仍会拒绝非快进覆盖，但没有 PR 审核关口，逻辑错误可直接进入共享主线。推荐情景 2；不能自动把用户带到简化模式，也不能关闭已有保护来配合它。

- 开工和推送前联网检查；每人仍有独立 clone。
- 推送被拒且分叉时，AI 推荐保留双方历史的普通 merge，先预演、解决冲突、再测试，不能强推。
- 只落后且工作区干净时，可使用 `safe_sync.sh` 快进。
- 这个脚本不自动处理分叉；非零退出后不能继续串联 push。
- 每次推送核对实际结果并通知协作者；项目进入长期维护或需要正式发布时转 PR 流程。

## 情景 7：版本发布

**适用回答**：“这版能用了，帮我留一个正式版本。”

1. 先确认用户授权的是打标签、发布 Release，还是部署；三者不是同一动作。
2. 核实准确目标提交已进入指定的主线或维护分支、测试与审批满足项目规则。不能给未经确认的本地领先提交打发布标签。
3. 检查标签是否已存在；不要用现有版本号覆盖旧对象。
4. 对用户确认的单一版本创建附注标签，只推该标签，不用 `git push --tags` 扩大范围。
5. 回读远端标签的 peeled commit，核对与目标 SHA 相同。Release 说明列变化、兼容性与验证缺口。
6. 发布后发现问题，优先新补丁版本或 revert 后发布，不删除重打别人已经使用的标签。

## 附录 A：已有项目接入

### 本地有代码、没有 Git

先检查父目录是否为另一个仓库。若确实不是 Git 仓库且用户授权，保留文件，核查秘密后初始化；不要重新 clone 覆盖原目录。首次提交只包含审查过的路径。

### 远端已有、本地空目录

核实远端与权限后 clone 到新的授权目录，不在非空目录上覆盖。

### 本地与远端都有历史

1. 保存未提交工作与原始 refs；备份位置必须独立、唯一，不覆盖既有备份。
2. 核实 remote，fetch 后读取两边日志与 merge-base。
3. 有共同祖先：在独立整合分支/目录试合，保留双方提交，复核后按 PR 提交。
4. 无共同祖先：这不是普通同步。向用户说明“两份独立历史”，询问保留两边历史整合，还是在保留原仓库的前提下迁移指定内容；不自动加 `--allow-unrelated-histories`。
5. 任何方案都不允许强推覆盖远端或删除原始代码。不能把重新复制文件当作已经保留原历史。

## 附录 B：旧版维护与 hotfix

当主线在做新版、线上仍用旧版时，先确定受影响发布版本和修复基线。

- 从旧版验证过的标签或现有维护分支创建独立 hotfix 分支，不在活跃主线改完后冒充旧版补丁。
- 修复、测试、PR 合入维护分支，并按情景 7 发布新补丁版本。
- 如果修复先在主线完成，可将准确的修复提交 cherry-pick 到 hotfix 分支；冲突解决后重新测试旧版，不能因主线测试绿就省略。
- 旧版先修时，评估修复是否需要回流主线；需要则另开 PR，避免下个大版本重新引入问题。
- `release/1.x` 等名称只是示例，沿用项目约定。用户只授权代码修复时，不自动部署生产。
