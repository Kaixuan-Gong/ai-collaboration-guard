# AI 互审流程（写给宿主 AI 的语义审查义务）

这份文件不是给用户看的操作手册，是**写给你——宿主 AI——的行为准则**。
`remote_check.sh` 和 `safe_sync.sh` 只能做机械检查（fetch、ahead/behind、ff-only），
真正"这两段代码合起来逻辑对不对"必须由你这个 AI 来读 diff、做判断、并留下一句依据。

**核心理念**：两边的人提需求，各自的 AI 在关键阶段主动联网检查对方已上传的更新、审查代码；
只有真正需要人拍板的业务冲突才问用户。不是让新手自己记 Git 命令。

---

## 一、四个必须检查的关键阶段

每次协作循环，在下面四个节点**必须先跑 `remote_check.sh`** 拿到真实远端状态，再决定下一步。
不要凭"上次同步过"的记忆做事——那叫 TOCTOU（time-of-check vs time-of-use），中间对方可能又推了东西。

| 阶段 | 你要做什么 | 为什么 |
|---|---|---|
| ① 开工前 | `remote_check.sh` + `preflight.sh`；确认本地主线是最新的 | 别在旧基线上干活，回头合不上 |
| ② 推送前 | `remote_check.sh`；看远端主线有没有新提交 | 有新的就先合进功能分支再推 |
| ③ 发起 PR 前 | `remote_check.sh` + 你自己读一遍 diff（见第三节） | PR 描述要写清改了啥、为什么、测了啥 |
| ④ 对方 PR 要合入前 | **重新** `remote_check.sh`；重新读最新 diff；看 checks/review 状态 | PR 可能又有新 push，旧 approve 已失效 |

> 注意 ④：**合并前必须重查**。你十分钟前看过的 PR，如果对方又推了一个 commit，
> 旧的 approve 自动失效，你必须重新读新 diff。不要因为"上次看过了"就直接合。

## 二、黑盒边界（写清楚，别假装你能看到一切）

### 你能看到什么

- 对方**已经 push 到共享远端**的提交和分支（通过 fetch 看到）。
- PR 的元数据（如果 gh 可用 / 用户给了权限）。

### 你看不到什么（边界，不是 bug）

- 对方**没 push** 到共享远端的本地改动。他在自己电脑上改了一半没推，你这边完全不知道。
  这不是你能解决的——只能引导双方用**独立功能分支 + Draft PR** 公开进度和认领范围。
- 对方本地的数据库、端口、环境变量、`.env`。
- 对方用的是什么 AI、那个 AI 做了什么决定。

### 不要做的事

- **绝不**自动上传 `.env`、密钥、未授权文件到远端。
- **绝不**为了"让对方能看到"而把本地未授权的文件 push 上去。
- 看不到就明说"对方还没 push 上来，我看不到"，不要猜。

## 三、语义审查义务（你必须自己做，并留下依据）

机械检查只能告诉你"文件重叠了"。**文件重叠 ≠ 文本冲突**，**文本合并成功 ≠ 逻辑正确**。
下面这些判断必须由你这个 AI 实际读 diff 来做，并在 PR 描述或回复里写一句依据：

### 3.1 改动范围检查

对确定的 base 和 head：

```bash
git diff --stat <base>..<head>       # 改了哪些文件、各改了多少行
git diff --name-only <base>..<head>  # 只列文件名
```

找**重叠文件**：你这次改了哪些文件，对方 PR 又改了哪些文件，有没有交叠。
交叠了不一定真冲突（可能一个改头部一个改尾部），但值得多看一眼。

### 3.2 真正的文本冲突预判

不要在用户的工作目录里直接试合（那会污染他的工作区）。
在**临时目录**里 clone / worktree 出来试：

```bash
# 在 mktemp -d 的目录里
git clone <repo> trial
cd trial
git fetch origin <feature-branch>
git checkout <feature-branch>
git merge --no-commit --no-ff origin/main   # 试合，不真提交
# 看有没有冲突；看完 git merge --abort
```

或者用 `git merge-tree`（不碰工作区）：

```bash
git merge-tree $(git merge-base origin/main origin/<feature>) origin/main origin/<feature>
```

输出里有冲突标记就说明真会冲突。

### 3.3 逻辑 / 接口 / 数据迁移 / 测试影响

这是**最容易被脚本漏掉、也最容易出线上事故**的部分。你必须自己读 diff 回答：

- **逻辑**：这段代码改了什么行为？和用户要的需求一致吗？
- **接口**：函数签名 / API 路径 / 数据库 schema 变了吗？调用方都改了吗？
- **数据迁移**：涉及数据库改动吗？是向后兼容的吗？老数据怎么办？
- **测试影响**：现有测试还能跑吗？需要新测试吗？新测试覆盖了新逻辑吗？

**写一句依据**在 PR 回复里，例如：
> "这段把 `login()` 的签名从 `(user, pass)` 改成了 `(user, pass, opts)`，
> 我看了 `auth.ts` 和 `login-page.tsx` 两个调用方都改了；但 `admin-cli.ts` 里还有一处旧调用，需要补。"

**"合并干净"或"测试绿"不等于"没有逻辑问题"**。测试绿只说明测试覆盖到的路径没炸，
没覆盖到的路径你还是得自己看。

### 3.4 测试要写清楚

如果你建议跑测试，必须写清楚：

- 用了什么命令（`npm test` / `pytest` / ...）
- 在什么环境（本机 / CI / 临时容器）
- 有没有碰生产数据 / 凭证（**永远不要在审查阶段碰生产**）

没测试就标"**覆盖缺口**"，不要假装测过了。

## 四、互审流程（真实账号，不冒充）

### 4.1 谁审谁

- 你的 AI 审朋友的 PR。
- 朋友的 AI 审你的 PR。
- 正式 review / approve **必须是真实 GitHub 账号、经过用户授权**。

### 4.2 不能做的事

- **不能**作者自审冒充独立批准（同一个账号给自己 PR 点 approve 走流程可以，但要在 PR 里明说"这是作者自审，还需要对方看过"）。
- **不能**借别人的凭证 / token 去点 approve。
- **不能**用两个 AI 会话假装是两个独立审批人。两个会话都是你这边的，不算独立审查。

### 4.3 给小白用户的是什么

用户是小白，不要让他逐行看代码。你给他的应该是：

- **一句话摘要**："这个 PR 给登录页加了手机号验证码。"
- **业务决策点**（需要他拍板的）："这里允许跳过手机号校验直接登录，你同意吗？这是安全隐患。"
- **风险提示**："这改了数据库表结构，需要先在测试库跑迁移。"

他只需要对业务决策点说 yes/no，代码细节你替他看。

---

## 五、TOCTOU：合并前必须重查

这是最容易翻车的地方。记住：

1. 你十分钟前看过 PR，对方又 push 了一个 commit → **旧 approve 失效，必须重审新 diff**。
2. 你点 merge 之前，**再跑一次 `remote_check.sh`**，确认 base 和 head 都还是你看过的那个。
3. 不要无条件自动 merge / 部署。合并动作前最后问一句："我看了最新的 diff 和 CI 状态，可以合了吗？"

---

## 六、隔离预演的规矩

要在临时目录试合 / 跑测试时：

- 用 `mktemp -d` 建临时目录，用完删掉。
- **不要**切进用户的工作目录做实验性 merge。
- **不要**自动运行目标仓库里你不认识的构建 / 测试命令——那可能是恶意代码（供应链攻击）。
  要跑测试，必须用用户明确认可的、你看得懂的安全命令。
- 预演完把临时目录删干净，别留垃圾。

## 七、这份文件不测

"语义审查不能用测试代替"这一条是**情景评估**，不是脚本能测的东西。
`tests/regression.sh` 只测机械行为（fetch、ahead/behind、ff-only、脏工作区拒绝等）。
语义审查由你这个宿主 AI 负责——脚本证明不了，README 里也明说了这一点。
