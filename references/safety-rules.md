## 一、绝对禁止（除非用户明确同意）

| 操作 | 默认态度 | 什么时候才可以 |
|---|---|---|
| `git push --force` / `--force-with-lease` | **禁止** | 仅当分支只有你一人在用、你刚推过、且已向用户解释后果并得到同意。共享分支/主分支永远禁止 |
| `git reset --hard` | **禁止** | 会丢掉未提交的改动。必须先 `git status` 展示会丢什么，用户确认后才可用 |
| `git clean -fd` | **禁止** | 会删掉未跟踪文件（可能是用户刚写的代码）。必须先展示会删什么 |
| `git checkout .` / `git restore .` | **禁止** | 静默丢弃工作区改动 |
| `git branch -D`（强删分支） | 先问 | 确认该分支没有未合并、未推送的提交 |
| `git commit --amend` 后强推已共享的提交 | **禁止** | 改写别人已经基于其上工作的历史 |
| 删除远端分支 | 先问 | 确认没有人还在基于它开发 |

**不要**为了"让命令跑通"而加这些参数。它们看起来省事，代价是把人本地的工作弄没。

## 二、push 被拒绝怎么办（重要纠正）

新手最容易犯的错：看到 `! [rejected]` 就加 `--force`。**这是错的。**

真实情况：正常 push 用的是"快进"规则。当远端已经有你本地没有的提交时，Git **默认拒绝**你的 push
（报 `non-fast-forward` 或 `! [rejected] main -> main (fetch first)`），这是它在**保护远端历史不被你悄悄覆盖**。

正确做法（按顺序）：

```bash
git fetch origin          # 把远端最新拉下来，但不自动合并
git status                # 看清楚你本地领先/落后多少
# 二选一：
git pull --rebase origin <你的分支>   # 把你本地的新提交"接在"远端后面，历史更干净（推荐）
# 或者
git pull --no-rebase origin <你的分支> # 生成一个合并提交，适合新手
```

解决完冲突（见 conflict-resolution.md），**正常 push**：

```bash
git push origin <你的分支>
```

只有一种情况考虑 `--force-with-lease`：你在自己刚推的、没人协作的个人分支上做了 `commit --amend` 或 rebase，
且 `git fetch` 后远端没被别人动过。即便如此，也要先跟用户说清楚。

## 三、保护未提交的工作

开工前先 `git status`。看到下面任何一种，**不要**直接 pull / merge / rebase / 切分支：

- `Changes not staged for commit`（改了没提交）
- `Untracked files`（新文件没加进 Git）

正确处理（让用户选，不要替他选）：

- **继续手上的活** → `git add -p && git commit -m "..."` 先存个档。
- **现在不想提交，想先同步远端** → `git stash push -m "WIP 提示"`，同步完再 `git stash pop`。
- **放弃手上的活** → 必须用户明确说"不要了"，并先 `git stash` 备份一份再清，不要直接删。

`git stash` 是安全网：它把未提交改动收起来，工作区变干净；`git stash pop` 再放回来。

## 四、敏感信息与 .gitignore

第一次往仓库提交之前，先确认 `.gitignore` 把这些挡住了：

- `.env`、`.env.*`、`.env.local`
- 各种密钥：`*.pem`、`*.key`、`id_rsa`、`*.p12`、`secrets.json`
- 依赖目录：`node_modules/`、`venv/`、`__pycache__/`
- 构建产物：`dist/`、`build/`
- 系统文件：`.DS_Store`

**已经误把密码/密钥提交进去了怎么办？** 告诉用户："这个密钥已经在 Git 历史里了，光删文件再提交不够——
历史里还留着。最稳妥的做法是**先去对应平台把这个密钥作废/轮换**，然后我们再清理历史。" 清理历史（`git filter-repo`
或 force push 重写）是高风险操作，必须用户明确同意，且优先用"轮换密钥"这种不碰历史的办法。

绝不要把用户的真实邮箱、本机用户名、绝对路径写进提交信息、README 或示例里。

## 五、分支保护 / PR / CI 的真实边界

**能做到什么、做不到什么，如实说，不要美化：**

- **分支保护规则**（禁止直接推主分支、要求 PR、要求必过检查）：只有仓库 **owner** 能在
  GitHub 网页 `Settings → Branches → Branch protection rules` 里设置。免费账号的公开仓库**可以**用基本的分支保护，
  但"要求 reviewer 批准""要求 status checks 通过"在某些私有仓库/计划上才有。先去设置页看得到什么，就说什么。
- **PR 互相 review**：真实两个 GitHub 账号时，互相 review 是有意义的。**同一个账号给自己 PR 点 approve**
  不算真审查——可以用来走流程，但要告诉用户"这是你自己审自己，对方最好也点进来看看"。
- **CI 自动检查**：如果加了 GitHub Actions，**必须确认它真的会跑、真的会变绿**：
  - 不要写一个 `paths: [ 'src/only-changed-by-nobody/' ]` 这种永远不触发的过滤，否则 PR 永远卡在 pending。
  - 不要把"要求必过"套在一个根本跑不起来的 workflow 上，那样谁都合不进去。
  - 合并前真的去 PR 页面看一眼检查状态：绿了再合，红了就看日志修，别靠"应该没事"。
- **不要假装自动化已经兜底**："放心，CI 会拦住坏代码"——如果根本没配 CI，或 CI 没跑，这句话就是假的。
  说"目前还没有自动检查，合并前麻烦你自己跑一下 / 看一眼"。

## 六、破坏性操作前的话术模板

动手前先输出一段这样的话（举几个例子）：

- 要 force push："远端 `feature/x` 上有你 10 分钟前推的提交，现在我要把本地改写后的历史强推上去。
  如果朋友也基于这个分支拉过代码，他下次 pull 会乱。**确认这个分支只有你一个人在用吗？**"
- 要 reset --hard："`git status` 显示你有 3 个文件改了还没提交，`reset --hard` 会**丢掉这些改动**。
  要我先帮你 stash 存一份再重置吗？"
- 要删分支："本地分支 `experiment` 上还有 2 个没合并进主分支的提交。删掉就找不回来了（除非 reflog）。
  确定要删吗？"
- 要切分支："你现在在 `main` 上有未提交改动，切到 `feature/y` 会把这些改动带过去。
  先提交 / 先 stash，还是你其实想留在 main 上改完？"

## 七、什么情况下要停下来问用户

出现以下任一情况，**停下来用大白话问**，不要自己拍板：

1. `git status` 很脏，但用户要你"同步一下"或"切个分支"。
2. push 被拒，且看起来远端历史和你本地分叉得比较远（不是简单落后）。
3. 冲突涉及**你不懂的业务文件**或**朋友刚改过的核心文件**。
4. 需要 force push / reset --hard / 改历史 / 删远端分支。
5. 要把代码推到一个你不确定权限的远端（不是 origin）。
6. 你不确定这是哪种协作情景（回到 SKILL.md 的"大白话提问"）。
7. CI 红了但用户说"直接合吧"——先告诉他为什么红、影响什么，再决定。
